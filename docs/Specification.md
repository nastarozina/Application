# Спецификация требований 0.1

**Проект:** Ne-Avito — веб-приложение просмотра и размещения объявлений.

## 1. Назначение продукта

Ne-Avito — веб-приложение, предназначенное для размещения объявлений о продаже товаров и поиска интересующих товаров другими пользователями. Система позволяет публиковать объявления с названием, описанием, категорией и фотографиями, просматривать список доступных объявлений и открывать подробную информацию о выбранном объявлении.

Backend построен на основе Spring Boot и разделён на независимые сервисы. Для хранения объявлений и категорий используется MongoDB, для хранения изображений — S3-совместимое объектное хранилище MinIO. Для хранения аккаунтов используется PostgreSQL. Также создан единый входной шлюз `inbound-gateway`.

Проект включает веб-интерфейс на React, серверную часть на Java и Spring Boot, контейнерную конфигурацию Docker Compose.

**Результат для пользователя:** возможность создать объявление с описанием, категорией и фотографиями, сохранить его в системе и предоставить другим пользователям возможность ознакомиться с опубликованной информацией и связаться для приобретения.

## 2. Пользователи

- **Продавец** — размещает объявление для нахождения покупателей.
- **Покупатель** — просматривает ленту объявлений, связывается с продавцом для приобретения товара.
- **Гость** — просматривает доступные объявления, изучает товары.

## 3. Основной сценарий

1. Пользователь открывает веб-приложение Ne-Avito.
2. Система загружает список объявлений и доступных категорий через API.
3. Пользователь просматривает объявления и при необходимости открывает подробную страницу выбранного объявления.
4. Для размещения товара пользователь открывает форму создания объявления.
5. Пользователь вводит название и описание, выбирает категорию и добавляет одну или несколько фотографий.
6. Frontend проверяет заполнение обязательных полей и подготавливает выбранные изображения к загрузке.
7. Система сохраняет и публикует объявление.
8. Объявление становится доступно покупателям, которые могут его просматривать и связаться с продавцом.

Основной сценарий может быть расширен регистрацией и авторизацией пользователей.

## 4. Обработка ошибок

- Отсутствие обязательных данных при создании объявления — форма не отправляется либо сервер отклоняет некорректный запрос.
- Несуществующая категория — система не должна создавать объявление с несуществующей категорией.
- Несуществующий идентификатор объявления — API возвращает `404 Not Found`.
- Некорректный запрос — API возвращает соответствующий HTTP-статус и информацию об ошибке.
- Неподдерживаемый формат или недопустимый размер изображения — загрузка отклоняется с сообщением об ошибке.
- Ошибка загрузки изображения в MinIO — операция не должна считаться успешно завершённой.
- Ошибка взаимодействия между сервисами — ошибка обрабатывается на серверной стороне и передаётся клиенту в согласованном формате.
- Ошибка загрузки списка объявлений — пользователь должен получить информацию о невозможности загрузить данные.
- Ошибка регистрации или авторизации — пользователь должен получать понятное сообщение без раскрытия конфиденциальных сведений.

## 5. Функциональные требования

**FR-01. Просмотр списка объявлений.** Пользователь может получить список объявлений, сохранённых в системе. При открытии страницы frontend отправляет запрос к API и отображает полученные данные.

**FR-02. Просмотр отдельного объявления.** Пользователь может открыть объявление по его идентификатору. Система возвращает информацию о выбранном объявлении, его категории и изображениях.

**FR-03. Создание объявления.** Пользователь может создать объявление, указав название, описание и категорию. После успешного выполнения операции объявление сохраняется в MongoDB.

**FR-04. Выбор категории.** При создании объявления пользователь может выбрать категорию из списка, полученного от сервиса категорий.

**FR-05. Просмотр иерархии категорий.** Система поддерживает категории с родительскими и дочерними элементами. В интерфейсе дочерние категории отображаются в составе соответствующей родительской категории.

**FR-06. Выбор изображений.** Пользователь может выбрать несколько изображений для нового объявления. До отправки формы выбранные файлы отображаются в виде предварительных изображений.

**FR-07. Удаление выбранного изображения.** Пользователь может исключить фотографию из выбранного набора до завершения создания объявления. Удалённый из формы файл не должен загружаться как часть этого объявления.

**FR-08. Загрузка изображений.** Система предоставляет механизм загрузки изображений в S3-совместимое хранилище MinIO. Frontend получает URL загрузки, передаёт файл в хранилище и завершает операцию через backend API.

**FR-09. Сохранение изображений объявления.** Backend сохраняет сведения об изображениях, связанные с идентификатором объявления. После повторного получения объявления система возвращает сохранённые сведения об изображениях.

**FR-10. Навигация к объявлению.** Пользователь может перейти из списка объявлений к подробной странице выбранного объекта. URL страницы должен содержать идентификатор соответствующего объявления.

**FR-11. Поиск объявлений.** Пользователь должен иметь возможность искать объявления по названию. Результат поиска должен содержать только объявления, соответствующие поисковому запросу.

**FR-12. Фильтрация по категории.** Пользователь должен иметь возможность ограничить список объявлений выбранной категорией.

**FR-13. Редактирование объявления.** Система должна поддерживать обновление ранее созданного объявления. При изменении отдельных полей передача `null` не должна приводить к непреднамеренному удалению прежних значений. Для текстовых полей, где это предусмотрено контрактом API, пустые и пробельные строки не должны заменять существующие значения.

**FR-14. Удаление объявления.** Система должна поддерживать удаление объявления по идентификатору. После успешного удаления объявление не должно возвращаться в списке и при запросе по прежнему идентификатору.

**FR-15. Регистрация и авторизация.** Пользователь должен иметь возможность создать учётную запись и войти в систему. Для организации аутентификации предусмотрена интеграция с Keycloak.

**FR-16. Управление собственными объявлениями.** Авторизованный пользователь должен иметь возможность просматривать и изменять собственные объявления. Операции изменения и удаления должны быть доступны только пользователям с соответствующими правами.

**FR-17. Связь с продавцом.** Покупатель должен иметь возможность связаться с продавцом заинтересовавшего его товара. В перспективе предусматривается чат для обмена сообщениями в реальном времени.

**FR-18. Валидация изображений.** Система должна проверять допустимость изображений перед загрузкой. Некорректные файлы должны отклоняться с соответствующей ошибкой.

**FR-19. Валидация обязательных полей.** При создании объявления система должна проверять заполнение обязательных полей. Некорректные данные не должны приводить к созданию объявления.

**FR-20. Обработка отсутствующих ресурсов.** При запросе несуществующего объявления или категории API должен возвращать соответствующую ошибку 404.

## 6. Нефункциональные требования

**NFR-01. Разделение ответственности.** Backend должен состоять из независимых сервисов, разделённых по областям ответственности. Сервисы объявлений и категорий должны иметь отдельные API и собственную бизнес-логику.

**NFR-02. Единый входной шлюз.** Взаимодействие frontend с backend должно осуществляться через `inbound-gateway`, обеспечивающий единую точку входа для API-запросов.

**NFR-03. Сохранность данных.** Объявления, категории и сведения об изображениях должны сохраняться в постоянном хранилище. После перезапуска контейнеров данные должны оставаться доступными при сохранении соответствующих томов.

**NFR-04. Разделение хранения данных.** Основные сведения об объявлениях и категориях должны храниться в MongoDB. Сами файлы изображений должны размещаться в MinIO, а в MongoDB должны сохраняться необходимые сведения для связи изображений с объявлениями.

**NFR-05. Контейнеризация.** Компоненты приложения должны запускаться в Docker с использованием конфигурации Docker Compose. Это обеспечивает воспроизводимость окружения и упрощает развёртывание проекта.

**NFR-06. Автоматизированная сборка.** При изменении исходного кода соответствующие проекты должны проходить автоматизированную сборку посредством GitHub Actions. Результаты выполнения workflow должны быть доступны в репозитории.

**NFR-07. Конфигурируемость.** Адреса сервисов, порты и параметры подключения должны задаваться через конфигурацию и переменные окружения, а не быть жёстко привязаны к исходному коду.

**NFR-08. Согласованный контракт API.** Backend должен возвращать корректные HTTP-статусы и согласованную структуру ответов. Клиент должен иметь возможность различать успешные операции, ошибки валидации и отсутствие ресурсов.

**NFR-09. Контроль версий.** Исходный код frontend и backend должен храниться в Git-репозиториях. Изменения должны фиксироваться коммитами и объединяться с основной веткой с использованием Pull Request.

**NFR-10. Согласованность данных.** Сведения об изображениях должны корректно связываться с соответствующим объявлением. При загрузке нескольких изображений каждое успешно загруженное изображение должно иметь отдельную запись и корректную связь с объявлением.

**NFR-11. Безопасность конфигурации.** Пароли, секреты и другие конфиденциальные параметры не должны храниться в открытом виде в исходном коде и публичных файлах репозитория. Для аутентификации предусматривается использование Keycloak.

**NFR-12. Проверяемость.** Основные операции backend должны покрываться автоматизированными тестами. Интеграционные тесты должны проверять взаимодействие с MongoDB и внешними зависимостями в предусмотренных сценариях.

## 7. MVP и резерв

### MVP

В минимально работоспособную версию входят:

- вход
- регистрация
- просмотр списка объявлений;
- просмотр подробной информации об объявлении;
- создание, обновление, удаление своих объявлений;
- выбор нескольких изображений и предварительный просмотр при создании объявления;
- удаление выбранных изображений до отправки формы;
- связь в реальном времени с продавцом через чат

### Резерв функциональности

В резерве находятся следующие возможности, которые могут быть реализованы после завершения основного сценария:

- уведомления;
- добавление объявлений в избранное;
- отзывы и оценки

Приоритет реализации определяется влиянием функции на основной сценарий, сложностью разработки и доступным временем.

## 8. Правила репозитория и Definition of Done

### Организация исходного кода

Backend хранится в репозитории [nastarozina/Application](https://github.com/nastarozina/Application). В его структуре выделены проекты `banner-api`, `category-api`, `inbound-gateway` и каталог `deployment` с конфигурацией развёртывания.

Frontend хранится отдельно: [nastarozina/frontend](https://github.com/nastarozina/frontend).

### Работа с изменениями

1. Для значимого изменения формулируется задача с описанием ожидаемого результата.
2. Для выполнения задачи создаётся отдельная функциональная ветка, например `feature/14-s3-image-storage`.
3. Изменения фиксируются коммитами с понятными сообщениями.
4. После выполнения задачи создаётся Pull Request в целевую ветку.
5. Перед слиянием проверяются корректность реализации, результаты сборки и предусмотренные тесты.
6. После успешной проверки изменение объединяется с основной веткой.

### Definition of Done

Изменение считается завершённым, когда:

- реализовано требуемое поведение;
- соблюдены согласованные контракты API;
- обработаны предусмотренные ошибки;
- проект успешно собирается;
- связанные автоматизированные тесты проходят;
- изменение зафиксировано в Git и отправлено в удалённый репозиторий;
- Pull Request проверен и объединён в соответствии с принятым процессом разработки;
- документация обновлена, если изменение затрагивает API, конфигурацию или порядок запуска.


## 9. Проверка требований

Проверка проводится на нескольких уровнях:

- **Модульное тестирование** — проверка отдельных методов и компонентов бизнес-логики.
- **Интеграционное тестирование** — проверка взаимодействия backend с MongoDB и внешними сервисами, включая проверку ответов зависимостей.
- **Проверка API** — отправка HTTP-запросов и проверка статусов, содержимого ответов и обработки ошибочных ситуаций.
- **Проверка frontend** — проверка отображения списка объявлений, навигации, заполнения формы, выбора и удаления изображений.
- **Проверка загрузки изображений** — создание объявления с несколькими фотографиями и проверка сохранения файлов в MinIO и связанных записей в MongoDB.
- **Проверка сборки** — запуск Gradle-сборки backend, сборки frontend и проверка результатов GitHub Actions.
- **Проверка развёртывания** — запуск окружения через Docker Compose и проверка доступности необходимых компонентов.
